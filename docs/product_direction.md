## 핵심 경험: 사진첩과 만남 기록의 역할

사진첩은 사진을 탐색하는 공간, 만남 기록은 이날의 이야기를 읽는 공간으로 구성한다. 상세의 대표 사진을 누르면 기존 전체 사진 뷰어가 열리므로 어떤 사진도 접근할 수 없게 되지 않는다. 사진이 없어도 장소, 메뉴, 사람을 담은 기록으로 보여준다.

다음 핵심 기능은 **‘그날의 이야기’ 본문**을 권장한다. 제목과 별도로 1~2,000자 선택 입력, 줄바꿈 유지, 기존 기록은 NULL로 호환한다. 기존 `save_meetup_atomic` RPC와 생성/수정 트리거가 있는지 확인하고, 본문도 사진·참석자와 같은 트랜잭션으로 저장해야 한다. 사진마다 글을 강제하지 않는다. 역할별 본문 수정·삭제도 기존 작성자 규칙을 그대로 따른다.

두 번째는 감정 1개(즐거웠어요/편안했어요/설렜어요 등)와 장소 타임라인이다. 자유 본문을 먼저 출시해 사용 여부를 보고 확장한다. 댓글, 반응, 투표를 한 번에 도입하면 알림·차단·삭제 정책도 필요하므로 뒤로 둔다.

홈의 다음 매력은 ‘작년 오늘’과 ‘한 달 돌아보기’다. 첫 페이지 5건만 보고 과거 추억이나 월간 전체 통계를 계산하지 않는다. 사용자의 활성 모임만 대상으로 날짜 범위를 조회하는 서버 API가 필요하다. 앱을 열 때 실제 추억이 있을 때만 보여주고, 없는 경우 추억 서랍을 유지한다.

## 참석률과 공정한 설명

현재 서버 참석률의 분모는 그룹 전체 기록 수다. 이번 화면은 이 정의를 명시한다. 가입 전 만남도 포함되므로 ‘성실도’, ‘개근’, ‘최하위’ 같은 표현을 쓰지 않는다. 참석 횟수 중심으로 돌아보게 한다. 기록 한 건에 여러 참석 ID가 중복되어도 상세 인원 수는 ID 집합으로 계산한다.

가입 후 참석률을 추가하려면 탈퇴·재가입 기간을 저장하는 별도 membership_periods 이력이 필요하다. `joined_at` 하나로 여러 재가입 기간을 재구성할 수 없다. 과거 날짜의 기록을 나중에 만들 수 있으므로 생성일 대신 만난 날짜를 기준으로 한다. 날짜/시간대 정의를 먼저 확정해야 한다.

## 개인 기록 / 함께 기록

모임 생성 시 두 선택지를 제공하는 방향을 권장한다.

- **개인 기록:** 소유자만 조회·작성·수정·삭제. 수동 참석자는 로그인 계정이나 관리자 역할이 없는 ‘기록 속 사람’이다. 이름 입력 전 연락처 업로드를 요구하지 않는다. 친구·가족·커플·동아리 기록을 자유롭게 구성한다.
- **함께 기록:** 실제 계정을 초대해 활성 멤버로 등록. 수동 인물을 새로 추가하지 않는다. 현재 방장/부방장/작성자 권한 규칙을 적용한다.

`groups.record_mode`에 private/shared를 추가하고 DB RLS·가입 RPC·수동 멤버 생성 경로를 모두 보호해야 한다. 개인 기록에서 초대 링크를 만들지 못하게 하고, shared 그룹에서 계정 없는 신규 참석자를 직접 insert하는 것도 서버가 거부해야 한다. UI 숨김만으로 구현하지 않는다.

기존 모임은 실제 계정과 수동 참석자가 섞여 있을 수 있다. 자동 변환·수동 참석자 삭제를 하지 않는다. 기존 모임을 호환 모드로 유지한 뒤 소유자가 선택하는 전환 절차가 필요하다. 개인→함께 전환 시 어떤 기록/사진/수동 인물이 공유되는지 미리 보여주고, 수동 인물과 초대 계정을 이름만으로 연결하지 않는다. 함께→개인 전환은 다른 멤버의 기록 접근과 작성물 권리를 결정하기 전에는 제공하지 않는다.

커플은 shared의 템플릿으로 제공하면 된다. 기본 아이콘, 함께 시작한 날짜, 기념일, 월별 만남 요약이 차별점이다. 사용자 수를 영구히 2명으로 묶거나 성별·관계를 강요하지 않는다. 관계 종료 시 공유 해제·내 기록 보관 정책이 먼저 필요하다.

## 네이버 지도 후속 구현

사용자 세부 기획에 따라 **장소 검색+지도 묶음**을 구현했다. 만남 장소 입력 아래에서 검색 화면을 열고, 최대 5개 후보 또는 지도 길게 누르기로 한 장소를 선택한다. 이름/주소/위경도/출처는 `meetups.place`에 기록·참석과 같은 트랜잭션으로 저장한다. 위치만 제거하거나 장소 텍스트를 직접 수정할 수 있으며 기존 문자열 기록도 유지한다.

모임 상세 정보에는 전체 기록의 장소를 조회해 핀을 표시하고 핀 범위로 줌을 맞춘다. 같은 위치의 방문은 핀 하나로 묶고 횟수와 만남 목록을 제공한다. ‘우리가 자주 만난 지역’ 순위 항목을 누르면 해당 지역 핀으로 필터링한다. 주소가 없는 핀과 좌표 없는 과거 기록은 지역 순위에서 제외한다.

네이버 지도 SDK 플러그인은 Android/iOS용이며, 지도 키가 없거나 웹에서는 안내 영역을 표시한다. 비밀 검색 API 인증은 Supabase Edge Function에서만 사용한다. 지역 검색과 지도 SDK는 인증 설정이 별개다. **실제 DB 추가 SQL·검색 함수 배포·API 키 설정·네이티브 지도 검증은 미완료**다.

구 경계를 색칠하는 지도는 후속 단계다. 공식 행정구역 경계 데이터로 GeoJSON/polygon overlay를 구성할 수 있으므로 구별 지도 PNG를 직접 만들 필요는 없다. 사용 조건·좌표계·경계 기준 연도·행정코드 연결을 확인해야 한다. 여러 장소 저장도 이번에는 도입하지 않았다.

설정·서버/DB 변경·검증 범위는 [naver_maps.md](naver_maps.md)에 정리했다.

## 회원가입 순서

지금은 Google 가입 흐름을 완성하고, iOS 출시를 준비할 때 Apple 로그인을 다음으로 권장한다. Apple 심사 지침의 최신 조건과 적용 예외를 확인한다. 국내 사용자가 Google 때문에 가입을 포기하는지 측정한 뒤 Kakao를 판단한다. Email은 비밀번호 관리 대신 OTP/매직 링크를 후보로 두되 이메일 발송·딥링크·만료/재전송 제한을 준비해야 한다.

가입 공급자가 달라도 기존 초대, 프로필, 계정 삭제 흐름은 동일하게 동작해야 한다. 같은 이메일이라고 클라이언트에서 계정을 합치지 않는다. 공급자 연결·재인증·가입 취소를 서버 세션 기준으로 처리한다.

## 수익화 권장: 한 명이 결제하는 그룹 구독

가족/커플/친구 모임은 멤버 전원이 결제해야 쓰는 구조보다 한 명이 그룹 보관함을 업그레이드하는 구조를 먼저 실험한다. 권한과 결제는 분리한다. ‘슈퍼방장’이라는 관리자 역할을 만들지 않는다. 방장 위임·탈퇴가 결제 해지나 권한 이전을 자동으로 일으키지 않도록 결제자와 그룹 권한을 별도로 저장해야 한다.

가격은 출시 확정이 아닌 실험 후보로 **그룹당 월 3,990원**을 제안한다. 무료에서도 만남 기록·초대·기본 사진·기본 통계는 사용할 수 있게 하고, 유료 가치는 원본 보관/넉넉한 저장공간/여러 장소/기간별 회고·내보내기에서 만든다. 인원 수만 제한하면 초대 성장이 막힐 수 있으므로 초기에는 저장공간/원본 보관을 중심으로 실험한다.

사진 원본은 공개 클라이언트의 화질 옵션만으로 비용을 통제할 수 없다. 서버에서 그룹별 저장량, 파일 크기, 결제 entitlement를 검증하고 원본/표시용 파생 파일을 구분해야 한다. 현재 50MB 전역 제한과 비공개 bucket은 유지한다. 요금제가 끝나도 기존 기록을 삭제하지 않고 조회·다운로드를 유지하며 추가 업로드만 제한하는 방향을 권장한다.

예시 계산은 시장 수익 예측이 아닌 가정이다. 활성 그룹 1,000개 중 3%인 30개가 월 3,990원을 결제하면 월 매출 119,700원, 결제 수수료를 15%로 가정하면 101,745원이 남는다. 10% 전환으로 100개가 결제하면 각각 399,000원/339,150원이다. 30% 수수료라면 각각 83,790원/279,300원이다. 세금, 환불, 지도/DB/스토리지/전송/운영비는 별도로 빠지므로 이 금액은 순이익이 아니다.

적은 규모에서도 매출은 가능하지만 이익은 평균 업로드량·사진 재조회/전송량·결제 전환율에 달려 있다. 광고는 방문 빈도가 낮은 추억 앱에서 충분한 노출이 없을 수 있고 몰입을 끊으므로 초기 기본 수익모델로 권장하지 않는다. 우선 그룹 재방문률, 첫 기록/첫 초대 전환, 저장공간 사용량을 집계해 구독 가격을 검증한다. 개인정보나 사진 내용을 분석 로그에 넣지 않는다.

인앱 결제, 영수증 서버 검증, 복구/해지/환불, 스토어 정책 확인 전에는 결제 버튼이나 유료 기능을 활성화하지 않는다. 개인 기록용 유료 보관함은 그룹 구독의 전환이 확인된 다음 추가한다.

## 내일 실기기 확인

기존 5가지 관리자/작성자/탈퇴/재가입 검증을 그대로 진행한다. 추가로:

- 로그인 소개 4장, Google 로고, Fold 펼침/접힘과 큰 글자에서 버튼 접근.
- 신규 프로필 완료 후 안내 팝업, 안내 종료 후 초대 목적지 복귀. 기존 가입자는 안내가 다시 나오지 않는지.
- 홈 모임 만들기·추억 서랍 진입, 복귀 시 갱신, 계정 전환 시 이전 모임이 남지 않는지.
- 사진 없는 기록과 장소/메뉴/탈퇴자 참석 표시. 대표 사진 및 전체 사진 뷰어 접근.
- 장소 문자열의 네이버 지도 검색. 미설치/외부 링크 실패 시 오류 안내.
- ‘함께한 시간’ 탭의 전체 기록 수와 참석 횟수, 기록 삭제/재가입 후 갱신.

## 로그인·홈 복원과 지도 선택 후속 수정

브랜치: `feature/restore-screens-and-improve-map-picker`. `main`/`develop`에 직접 푸시하지 않는다.

로그인·홈은 이전 화면으로 복원했다. 지도는 우측 하단 확대 버튼·전체 화면 선택·빨간 위치 핀·700ms 입력 후보 검색·장소/주소 검색 선택·지도 중심 지역 보정과 거리순 후보를 추가했다. 네이버 지도 앱의 전체 POI/자동완성과 같은 기능이라고 표현하지 않는다.

클라우드 앱 설정의 검색 함수 주소는 404/NOT_FOUND로 확인했고, 사용자도 함수 배포·추가 SQL 미적용이라고 확인했다. SQL과 서버 함수는 이번 작업에서도 실제 프로젝트에 적용하지 않았다. 키 값이나 실제 제공자 인증 설정은 조회하지 않았다. 적용 파일과 배포 명령/Secrets는 [후속 안내](map_picker_followup.md)를 따른다.

후속 최종 검증: `flutter test --no-pub` 전체 **122개 통과**, 검색 서버 테스트 **10개 통과**, PostgreSQL 17 임시 DB에서 주소 출처 저장을 포함한 SQL 테스트 통과, 웹 빌드 성공, `git diff --check` 통과. `flutter analyze --no-pub`는 오류/경고 0, info 28개(복원한 로그인 화면의 기존 withOpacity 사용 포함)로 종료 코드 1. 실제 Android/iOS 빌드·네이버 인증/검색·Supabase 배포는 미실행.

## 지도 검색 UX 추가 수정

사용자는 서버 배포 후 검색이 동작한다고 확인했다. 같은 feature 브랜치에서 전체 지도 위 검색창·40px 검색 버튼·본문 글꼴 제목·결과 패널 상단 4px·장소/주소 자동 판별·범위 선택 제거·상호명 일치 후보 필터를 구현했다. 초기 지도 중심을 검색어에 붙이지 않는다. API 최대 후보 5개 한계는 유지하며, 새 SQL 없이 검색 함수를 재배포해야 한다. [최신 동작/재배포 안내](map_picker_followup.md)를 따른다.

지도 검색 UX 추가 수정 검증: Flutter 전체 **123개 통과**, 검색 서버 **14개 통과**, 웹 빌드 성공, 분석 오류/경고 0(info 28개), `git diff --check` 통과. 화면을 지도 전체로 채우는지, 검색 버튼 높이와 공통 글꼴 상속, 주소 자동 판별·상호명 필터·기본 중심 지역명 미추가를 검증했다. 실제 기기와 실제 네이버 결과는 자동 테스트 범위 밖이며 검색 함수 수정본은 사용자가 재배포해야 한다.
